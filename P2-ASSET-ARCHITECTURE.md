## Product and Asset Scope

Each commitment selects one settlement asset before activation. That asset and its network-specific token contract account are immutable for the commitment and included in its policy digest. A commitment never mixes assets or converts between them. The initial Console catalog offers native NEAR and Circle USDC only.

## Contract and Accounting Design

- Add a generic NEP-141 settlement backend to LCP rather than deploying one adapter per fungible token. For the first release, permit only native NEAR and the verified Circle USDC account for the current network. Keep the token-account catalog versioned in source and the Console/SDK. A future governance-managed registry is deferred; adding an asset after immutable deployment may require a new core deployment.
- Check the token contract account on every token callback. The commitment's asset and account are pinned; never trust a token symbol as identity.
- Keep amounts in smallest units: yoctoNEAR for native payouts and atomic token units for NEP-141. User-facing conversion uses the pinned asset catalog and checked integer arithmetic; never use floating-point amounts.
- Do not reinterpret existing fields such as `tranche_yocto` or `escrow_funded_yocto` as token units. Preserve existing Borsh layouts. Add versioned policy/asset and ledger sidecars keyed by commitment ID, treating a missing asset record as legacy native NEAR. Specify sidecar versioning and compatibility tests before implementation.
- Domain-separate the policy digest and bind asset kind, NEP-141 contract account (when applicable), and raw tranche amount. Version events and views with explicit `asset` and `amount_raw` fields; retain existing NEAR fields for legacy readers. Update SDK and indexer parsers before Console rollout.
- Native NEAR commitments keep the existing deposit and asynchronous payout/refund behavior. USDC funding arrives through `ft_transfer_call` and an LCP `ft_on_transfer` receiver. The sponsor attaches the NEP-141-required 1 yoctoNEAR security deposit to the token call, separately from the USDC amount and gas. The receiver checks the token contract, sender/sponsor, commitment state, and funding cap; it accepts only the amount needed and returns unused units so the NEP-141 resolver can refund them.
- USDC claims and residual refunds use `ft_transfer` with a private LCP callback. Persist pending state first; reconcile paid/refunded totals only after callback success; restore retryable state after failure. Reserve the NEP-141-required 1 yoctoNEAR transfer deposit from the caller's NEAR attachment in addition to storage growth, and return any remaining excess. Keep transfer nonces and duplicate-callback protection equivalent to native settlement.
- If the private callback receipt itself fails, the transfer remains pending. Never release that reservation by timeout: the token receipt may already have succeeded, making a second payout unsafe. NEP-141 itself provides no generic receipt proof. The separately reviewed `usdc-receipt-recovery` feature implements a strict receipt-certificate path locally and passed its initial isolated Sandbox scenarios; it remains disabled in the deployed contracts pending the remaining acceptance gates below.
- Keep `bounded-payout-adapter` NEAR-only in the first release. Reject or hide authority grants for USDC commitments until an asset-matched FT adapter has a separately reviewed design and tests.

## Registration, Storage, and UX

NEP-141 balances require token-contract storage registration. Compare each account's NEP-145 `total` against the token contract's current `storage_balance_bounds.min`; a non-null record alone is not enough. Before enabling USDC funding, verify the LCP account meets that minimum. Before payout or refund, perform the same check for the beneficiary or sponsor. Offer an in-app registration or top-up action, paying only the current shortfall in NEAR. Use `registration_only: false` for existing accounts because NEP-145 refunds deposits sent with `registration_only: true` to already registered accounts. Do not bake a storage price into policy. Explain that the commitment budget is USDC while gas and storage remain NEAR. Failed transfers must remain recoverable if registration changes between preflight and settlement.

Show the asset selector before budget entry and display an example of the resulting total and tranche in the selected units. Pin the token account and decimals in the curated network catalog, show the full contract account in review, and link to its network explorer. Use token metadata only as a consistency check, not as authority to change decimals after a commitment is created.

## Extensibility and Trust Boundaries

The first extensibility point is a generic NEP-141 backend plus a typed, versioned asset catalog, not a governance-managed token module framework. Adding a well-reviewed NEP-141 asset should require a catalog entry, metadata/address verification, and testnet acceptance, not new per-token transfer code; the immutable core's on-chain allowlist still means a new core deployment may be needed. Tokens with nonstandard callbacks or standards require a new backend and security review. This separates ordinary asset additions from an upgradeable on-chain token registry.

This design does not promise USDC redemption, a guaranteed dollar value, or issuer neutrality. Users must see the exact network and token contract they choose.

## Delivery and Acceptance Sequence

1. **Complete:** Freeze the first release scope as native NEAR plus verified Circle USDC; specify the versioned sidecar and migration approach. Defer an on-chain governance-managed asset registry.
2. **Implementation and local validation completed 2026-11-15:** The versioned asset sidecar, raw ledger, NEP-141 callbacks, legacy NEAR fields, and Borsh layouts are covered by contract tests. Tests verify asset-bound policy views/digests, rejection of an unapproved token, wrong-token/sender refunds, funding caps and activation gating, 1 yoctoNEAR transfer deposits, failed claim/refund recovery, duplicate-callback idempotency, pending reservation when a callback does not execute, and 24 receipt-order schedules. The callback action is asserted to receive 20 Tgas. The `lcp-core` suite passes 76 tests. Rust 1.100.0 is pinned across local development, CI, and reproducible contract builds; `rust-toolchain.toml`, `Cargo.toml`, and both NEP-330 images agree. The official `cargo-near 0.23.0` prebuilt CLI was checksum-verified on this x86_64 macOS host. Earlier full checks included both contract checks, evaluator WASM builds, JavaScript tests, Worker type/dry-run checks, Console build, and a zero-high npm audit. The source revision `e9074ddced4be9dce4dd4c1061909f7869054cf1` was reproducibly rebuilt and deployed as documented in [TESTNET-E2E-STATUS.md](TESTNET-E2E-STATUS.md). An implementation-team source review found no accounting defect in token allowlisting, sponsor-bound funding, caps/resolver refunds, pending reservations, callback reconciliation, failed-transfer recovery, duplicate-callback handling, or integer conversion. Independent source findings and live acceptance are reconciled in [P2-USDC-INDEPENDENT-AUDIT-FOLLOWUP.md](P2-USDC-INDEPENDENT-AUDIT-FOLLOWUP.md).
3. **Implemented and deployed to testnet:** SDK types and calls expose asset metadata and raw amounts. SDK tests assert the `ft_transfer_call` payload and 1 yoctoNEAR deposit, plus fresh-account registration and existing-account top-up arguments. The event indexer stores complete event JSON, so no D1 migration is needed for new asset fields. The Console supports asset selection, integer conversion, metadata checks, minimum-balance registration preflight, and NEAR-denominated registration/top-up costs. It displays the complete token account and network explorer link in creation and policy review.
4. **Testnet acceptance (2026-11-15):** Commitments `41`–`43` passed the funding/storage/refund, beneficiary payout and failed-claim retry, unused-operations refund, and overlapping funding checks. Callback receipts consumed 3.241–3.247 Tgas on the claim success/failure paths against a 20 Tgas allocation. Local stress tests cover 24 receipt orderings. All temporary funds and accounts were reconciled; see [TESTNET-E2E-STATUS.md](TESTNET-E2E-STATUS.md) and [the audit follow-up](P2-USDC-INDEPENDENT-AUDIT-FOLLOWUP.md).
5. **Recovery implementation and isolated acceptance (2026-11-16):** The v4 [recovery design](P2-USDC-RECEIPT-RECOVERY-DESIGN.md) is implemented locally behind `usdc-receipt-recovery`; it remains disabled in the deployed contracts. The independent implementation follow-up approved isolated VM/Sandbox acceptance after closing its five source/package findings. NEAR Sandbox 2.14.0/protocol 88 passed callback-first and certificate-first settlement, a callback/certificate race, failed-transfer recovery/retry, payer-credit and storage-reserve accounting, exact/underfunded native cash boundaries, multiple outflows, aggregated failed refunds, governance rotation boundaries, and rollback after a runtime overflow. Follow-up cases rejected 0–3 signatures and five invalid signatures, accepted valid 4-of-5 and 5-of-5 certificates, rejected canceled-proposal replay and retired-key reuse, and verified permissionless storage-release retry after a 1 Tgas failure. Measured recovery receipts used 15.512 Tgas (4-of-5) and 17.472 Tgas (5-of-5); these observations are not a worst-case gas bound. The callback OOG path used a 1 Tgas allocation. Native callback, transfer rollback, and same-receipt action-order cases are recorded separately. Results and artifact hashes are in [the Sandbox guide](tests/sandbox-usdc-callbacks/README.md). The governance timing test uses a ten-second fixture-only minimum; production retains seven days, which was not elapsed in the Sandbox run. These results do not complete the full acceptance matrix or authorize a canary. Still open are delayed/missing callback stress and phase-specific liquidity limits, remaining receipt/configuration/migration/gas-boundary cases, independently administered operator replay/signing drills, independent artifact reproduction, and a separately authorized testnet canary. Keep predecessor liabilities separate; this feature does not prove an in-place migration. Deliberate issuer pause/restriction testing remains deferred on the shared testnet token. Reverify Circle's mainnet USDC contract and code provenance at release time.
