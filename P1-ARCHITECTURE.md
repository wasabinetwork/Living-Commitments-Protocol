## Design constraints

- NEAR remains authoritative for policy version, time, health, challenge state, eligibility, and settlement. Evaluators only return bounded evidence outcomes.
- v1 and v2 policy digests and evidence formats remain immutable. Advanced evidence and governance use a new versioned format and separate storage prefixes; contract state layout must not be changed in place without a migration plan.
- The current heartbeat payload is included in the public `request_evaluation` transaction. A file selected in the browser stays local, but its digest and signed payload are public. The current flow does not provide private evidence access.
- Evidence confidence must describe inspectable provenance and agreement. It must not imply a probability that the underlying claim is true.

Independent probe operators submit observations for each evaluation. Source-policy schema v1 pins public keys and accepts raw Ed25519 or NEP-413-signed reports for existing commitments. New schema v2 policies list unique source IDs and NEAR operator accounts without public keys. Each operator opens the commitment on their own device, connects the listed account, and submits the report in a standard NEAR transaction. The contract checks `predecessor_account_id`, records the authenticated submitter in the inbox entry, and adds that contract-derived account to evaluator input. V2 reports can be evaluated only through the inbox path; the public raw-report method remains for legacy v1. A wallet transaction binds the report to an account but does not prove that the observation is honest or that a real endpoint was probed.

The Console creates the private target salt/fingerprint in-browser. Its in-app health check is limited to the same HTTPS origin as the Console; external targets retain the standalone tool `evaluators/service-availability/probe.mjs` for legacy v1 reports. A report binds the contract, commitment, evaluation, policy digest, endpoint fingerprint, source and operator IDs, observation time, status class, and latency. The evaluation ID prevents replay across evaluations, and the evaluator counts at most one report per source. The endpoint fingerprint is `SHA-256(salt_bytes || canonical_HTTPS_URL_UTF8)`; operators keep the URL and salt off-chain.

For a three-operator policy, a sample rule could require two independent `up` reports, define acceptable HTTP status and maximum latency, and cap report age. The count must be a strict majority, so `up` and `down` cannot both form a quorum. A minimum corroboration threshold can require stronger agreement than the minimum count; for example, 7,000 basis points over three configured operators requires all three to agree. Two valid `down` reports produce `NonCompliant` only when both thresholds are met. Reports that are missing, stale, invalid, or split without a quorum produce `Inconclusive`; they do not prove the service is down. An inconclusive result does not refresh the last-good evidence clock, so existing temporal rules still apply.

The result reports the number of valid independent operators that agree, the configured denominator (for example, `2 of 3`), and coverage in integer basis points. This is source agreement coverage, not a truth probability. Treat evidence confidence as a structured description of signature validity, source diversity, report freshness, agreement, and separately verified evaluator attestation; do not collapse it into one probability-like score. Distinct keys do not prove distinct ownership; the policy parties choose and review the operator roster. TEE attestation proves that the pinned evaluator applied the rules to the reports, not that an operator performed an honest probe.

OutLayer's WASI Preview 2 runtime supports HTTPS requests, so a direct TEE probe is technically possible. It would remove the multi-operator workflow but concentrate observation in OutLayer's network environment; passing an endpoint in the public NEAR execution input would also reveal it. Keep this as a separately labeled future mode requiring a private input path and an explicit trust choice. Do not present it as equivalent to independent-source quorum evidence. This remains a parked alternative for a later design decision.

For new schema v2 policies, the NEAR report inbox lets each listed operator submit a report from a separate device with one wallet transaction; the sponsor reviews the public inbox and requests evaluation from collected reports. This removes the operator key-pinning and JSON/clipboard handoff while keeping endpoint URL and salt private; report contents themselves are public. The 4 KiB per-report limit is an application-level bound chosen to control persistent storage and evaluator input size, and to limit storage bonds under [NEP-145](https://github.com/near/NEPs/blob/master/neps/nep-0145.md). It is not a NEAR protocol maximum: [NEP-509](https://github.com/near/NEPs/blob/master/neps/nep-0509.md) specifies a much larger transaction-size limit (currently 1.5 MiB), while this evaluator request separately caps aggregate input at 32 KiB. Each source gets one staged report for the next evaluation, expiring within 15 minutes or at the source-freshness deadline. Operators fund storage; consumed, replaced, or expired reports create a withdrawable refund credit for the original operator. Evaluation IDs and policy/source hashes bind reports to the current request; exact report replays are rejected, consumed entries are removed before evaluation is scheduled, and policy amendments clear staged reports under the old digest. Inbox data uses versioned raw-storage sidecars so the existing Borsh contract-state layout stays unchanged. The v2 contract, evaluator, and Console preview are deployed; commitment `27` completed two separate-device testnet evaluations with 2/2 valid UP reports, and evaluation `#2` exercised report replacement and refund withdrawal. Exact replay rejection and expiry reclaim/refund were confirmed on testnet on 2026-11-11. The direct OutLayer TEE probe remains a separate future trust mode, not equivalent evidence.

To reproduce exact inbox replay rejection, open the Console preview with `?lcpReplayTest=1`, submit one transaction-authenticated v2 report, and use the opt-in control to submit the same report payload again before evaluation is requested. The preview-only control retains the just-submitted report in page memory and is not shown on production origins. See the step-by-step wallet flow in [CONSOLE-GUIDE.md](CONSOLE-GUIDE.md).

## Evidence privacy and reviewer access

No public email, chat handle, or upload inbox is added. Reviewers identify themselves with a NEAR account and submit a NEP-413 signed request naming the commitment, evidence digest, requested scope, recipient account, encryption-key fingerprint, expiry, and one-time nonce. The maintainer approves that exact request with a wallet signature. The independent review scope and release gates are documented in [the reviewer security brief](services/reviewer-access/SECURITY-REVIEW.md).

The local Console flow uses NEP-413 signatures for reviewer requests, maintainer approval/rejection, download, and revocation. Approval and revocation require a current maintainer FullAccess key; reviewer requests accept a current NEAR access key. The browser creates a salted file digest and a passphrase-encrypted X25519 key backup, encrypts the artifact with AES-256-GCM, and wraps its content key with HPKE. The Worker stores ciphertext in a private R2 bucket and consent/access metadata in D1, including the signed reviewer request and signed maintainer resolution envelopes; list APIs do not return those signatures. It limits download counts, expires requests and grants, purges ciphertext on revocation or expiry, and retries cleanup of unlinked ciphertext after interrupted grant writes. Access events are retained for 90 days; active grant/request metadata is retained while access is valid and terminal metadata, including consent signatures, for 90 days after closure and last access.

This is private reviewer collaboration, not proof that the file was evaluated on-chain. The salted digest is a separate private commitment; it is not the public `evidence_hash` in the NEAR evaluation record. Maintainer approval binds the chosen file to the request but cannot prove it is the original evidence source. Private evaluation still requires a separate TEE retrieval/decryption path. The testnet Worker is provisioned and deployed, but the Console integration remains disabled pending independent security review. Revocation cannot erase a copy already decrypted by a reviewer.

Private evaluation must keep plaintext out of NEAR transaction arguments. A future evaluator request should carry an opaque object reference and ciphertext digest; the TEE retrieves and decrypts the artifact with a per-commitment secret. OutLayer's NEAR `request_execution` accepts `secrets_ref: { profile, account_id }`; the WASI module receives decrypted values as environment variables, and a secret may be bound to a specific WASM hash. For LCP, the maintainer should own a unique secret per commitment, grant the LCP contract access through an explicit direct-call/`via` rule, and pin access to the reviewed evaluator hash. The secret must never appear in transaction arguments, stdout, callback JSON, or logs. OutLayer's access documentation distinguishes the outer transaction signer from the calling contract; live testnet grant/retrieval and input confidentiality remain unverified, so no current request should pass `secrets_ref`. Add this only through a versioned policy/input sidecar that preserves v1-v3 behavior. See the official [WASI guide](https://app.outlayer.ai/docs/wasi), [NEAR integration](https://app.outlayer.ai/docs/near-integration), and [secrets guide](https://app.outlayer.ai/docs/secrets).

## Multi-source policy and outcome model

An advanced policy contains a versioned source roster, operator identities, freshness bounds, domain rules, and an aggregation rule. Legacy v1 rosters also contain source-key fingerprints; transaction-authenticated v2 rosters omit them. The digest covers the canonical serialization of every field. The contract and evaluator reject duplicate operators, unknown sources, replayed reports, invalid signatures or submitter provenance, stale observations, and unsupported schemas.

The advanced result has three outcomes:

- `Compliant`: the configured quorum supports the service condition.
- `NonCompliant`: a valid quorum supports a policy-defined failure condition.
- `Inconclusive`: the source quorum or agreement threshold is not met.

The contract records `Inconclusive` without replacing last-good evidence or starting a negative-health clock. It cannot authorize a claim from that result. The Console shows source coverage, outcome, and reason codes separately from health. The evaluator returns only bounded summaries and hashes; private reports stay off-chain.

## Contract v3 integration boundary

The current v3 implementation does not add fields to the persisted Commitment, CommitmentPolicy, or EvaluationRecord Borsh structs. It stores the source policy and bounded evaluation summary in `lcp:service-policy:v3:<commitment_id>` and `lcp:service-summary:v3:<commitment_id>:<evaluation_id>` raw-storage keys, and includes their bytes in storage-bond accounting. Separate create/request/view methods keep v1/v2 call shapes stable. `Inconclusive` was appended after the two existing `Verdict` variants so their Borsh discriminants remain 0 and 1.

The v3 commitment digest is domain-separated over the base policy Borsh bytes and canonical source-policy JSON, with explicit lengths. The contract supplies the current NEAR block timestamp and next evaluation ID. Reports bind both digests and that evaluation ID. The caller cannot choose the trusted request timestamp. Source reports remain public transaction arguments; private or confidential evidence must wait for the encrypted reviewer/evaluator path.

The evaluator reports its oldest observation among the reports that satisfy the winning quorum. The contract checks that timestamp is not in the future, is within the temporal source-lag bound, is newer than the last accepted observation, and has not expired. A compliant outcome refreshes last-good evidence; a noncompliant outcome starts the negative clock; an inconclusive outcome is recorded as an evaluation result but changes neither health clock nor claim eligibility. Every outcome blocks claims while evaluation is pending, and only a compliant accepted record can govern a claim.

The implementation persists bounded source counts and agreement coverage in the v3 summary key, exposes them through optional JSON view fields, and keeps contract storage authoritative. Local tests cover sidecar storage, storage reservation, valid source-summary handling, and the unchanged-clock inconclusive outcome. The v3 upgrade preserved existing state: finalized reads still return commitments 8, 9, 19, and 21. Validate all three v3 outcomes and duplicate/stale callback handling in the pilot.

## Consent-based amendments

The v3 source-policy amendment sidecar binds the current digest, new digest, proposal nonce, expiry, and future effective timestamp. It requires a separate NEAR transaction from each distinct sponsor, maintainer, beneficiary, and arbiter account. Any required approver may reject a pending proposal before expiry, even after approving it; rejection leaves the active policy unchanged and releases the single pending slot. The proposer may also cancel, and anyone may record expiry after the deadline. The active policy stays in force until all approvals and the future boundary are satisfied. Activation starts a new initial evidence clock, clears prior compliant evidence for eligibility, and preserves the recurring budget schedule and existing failure/breach state. This feature does not amend base budget, evaluator, or role fields. The Console checks a read-only contract capability before showing the rejection action, so it remains hidden until the updated core is deployed.

Past evaluation records and settled transfers remain unchanged. New evidence must satisfy the new digest before it can support a claim. Proposal and activation are blocked while an evaluation or challenge is pending. Amendment sidecars preserve approval state and emit proposal, approval, activation, rejection, cancellation, and expiry events without changing persisted Borsh state.

## Contract-gated authority adapters

An authority grant is separate from the evidence policy. The sponsor or beneficiary can grant a named adapter a `bounded_payout` capability for one fixed recipient, with per-action and cumulative limits, expiry, increasing action nonce, one action per epoch, and revocation. Actions require the same on-chain eligibility as a tranche claim, including completed evaluation challenge window, funded escrow, current policy evidence, and Healthy state. The adapter also requires LCP to pass the grant creator and rejects the payout unless that account equals its configured pool manager. Thus a manager must also be the commitment sponsor or beneficiary to create an executable grant for that adapter. The sample adapter pays only from its own prefunded pool and reconciles failed NEAR transfers. The LCP grant allowance is consumed when the call is issued, even if the adapter call fails.

The sample adapter has an explicit pool-manager account that can recover available, unreserved pool funds through a reconciled transfer. Pending payouts and withdrawals cannot be withdrawn again; a failed transfer restores the pool balance. This is a local test implementation; no authority has been deployed or granted on testnet. Each target must explicitly implement the authorization interface. The grant pins an adapter account ID, not its code hash; its deployment administrator could replace the code, so test deployments should remove or tightly secure upgrade keys. A grant does not expose account keys, LCP escrow, generic calls, or authority over an account that did not consent. Cloud services and other off-chain effects need a separately reviewed relay and verifiable authorization path.
