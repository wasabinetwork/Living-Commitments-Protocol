# USDC Receipt-Recovery Reference Vectors

`golden-vectors.json` contains deterministic Borsh, domain-hash, Ed25519, and Base64 vectors for `RecoveryIntentV1`, `RecoveryCertificateV1`, `CommitteeRotationV2`, and `CommitteeRotationCancellationV2`. The same JSON is intended to be consumed by the Rust contract implementation and signer tooling.

Regenerate it with Node.js built-in crypto only:

```sh
node tests/receipt-recovery-vectors/generate.mjs
```

An independent Rust consumer reconstructs the Borsh encodings, domain hashes, 4-of-5 deterministic signatures, and envelopes, then checks valid signatures with `verify_strict`. Its bounded reference parser accepts canonical 4-of-5 and maximum-size 5-of-5 envelopes. Mutation cases cover Base64/Borsh bounds and canonicality, invalid versions and account IDs, inconsistent option tags and intent hashes, trailing bytes, insufficient/excess signatures, duplicate/unsorted/unpinned keys, and changed signatures. It also confirms that changing every recovery-certificate field or signing domain invalidates the original quorum and checks strict rejection of a changed message/signature, noncanonical `S`, weak/small-order public keys, and noncanonical public-key and `R` point encodings:

```sh
cargo run --locked --manifest-path tests/receipt-recovery-vectors/rust/Cargo.toml -- tests/receipt-recovery-vectors/golden-vectors.json
```

This is an offline reference utility, not contract or production signer code. It establishes positive vector parity, bounded reference-parser behavior, certificate-field/domain mutation behavior, and strict Ed25519 rejection cases in the pinned Rust library. It does not exercise the contract parser or verifier itself.

The governance half of this file is also a frozen conformance input for the contract. `contracts/lcp-core/src/contract.rs` includes `golden-vectors.json` at compile time, and `contract_parser_matches_the_committed_governance_vectors` (feature `usdc-receipt-recovery`) feeds the stored rotation and cancellation envelopes to `parse_and_verify_rotation_proposal` and `parse_and_verify_rotation_cancellation`. The contract must accept the Node-generated 4-of-5 signatures, reproduce the published domain digests, and re-serialize the parsed messages to the published Borsh bytes, so a change to either implementation breaks the test instead of silently drifting. Regenerating the JSON therefore changes a contract test input; run the Rust test suite after regenerating. The certificate vectors are not yet consumed this way, and the mutation and strict-Ed25519 cases still run only in the reference utility. VM-level acceptance of these cases remains an open gate.

All values are synthetic. The generator derives public test keys from public labels; the test seeds are intentionally reproducible and unsafe for any real account or committee. The token-code hash and receipt identifiers are not network observations or approved USDC configuration.

The vector set is synthetic. The repository freezes strict signature acceptance to `ed25519-dalek 2.2.0` `VerifyingKey::verify_strict` semantics; the NEAR protocol-88 host verifier alone is not sufficient. Rust parity proves the published positive encodings and signatures can be independently reproduced; it does not implement the Rust contract verifier. Parser and strict-Ed25519 mutations are generated by the Rust checker rather than stored as separate invalid binary fixtures in the JSON. Do not treat reference-parser acceptance as contract recovery acceptance or approval to deploy recovery.
