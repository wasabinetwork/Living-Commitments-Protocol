## Safety invariant

For each commitment, preserve `funded_raw = paid_raw + refunded_raw + pending_raw + free_raw`. One immutable transfer intent can settle exactly once:

- **Success:** move pending value to paid for a tranche, or refunded for an escrow refund.
- **Failure:** move pending value to free so an authorized retry can allocate a new transfer ID.
- **Unknown, conflicting, unsupported, or non-final:** make no accounting change; retain the reservation.

Never release pending value by elapsed time, token balance deltas, an administrator-selected result, or an unverified RPC response. A retry always gets a fresh, monotonically increasing transfer ID. Recovery is a threshold oracle, not a NEAR receipt proof or trustless light client.

## V1 committee and trust assumptions

Use **4-of-5 Ed25519 signatures**. Accept four or five unique valid signatures over the same digest; never accept fewer than four. A 4-of-5 quorum has an intersection of at least three keys. With at most two malicious keys, at least one signer in any two quorum intersection is honest, provided honest operators independently apply the same objective rule and durably sign at most one outcome per `(instance_id, transfer_id)`. This is an oracle assumption, not Byzantine consensus. Shared software, data, or provider faults can still cause correlated mistakes.

The liveness assumption is that four members can validate and sign; more than one unavailable or abstaining operator can leave a transfer pending. No sponsor, maintainer, beneficiary, arbiter, owner, or single administrator can override the result. If a pinned epoch is lost or compromised, its unresolved transfers remain pending indefinitely. Do not add a timeout, emergency key, or unilateral recovery path.

Operators must be separately administered, use separate signing keys and durable sign-once journals, and retain receipt archives for as long as their epoch has pending transfers. Each operator validates receipt inclusion, ancestry, and finality against its locally validated archival chain under the version-pinned procedure in [the operator-policy annex](P2-USDC-RECEIPT-RECOVERY-OPERATOR-POLICY.md), then cross-checks receipt identity/outcome with an independently administered source. A single provider response or a quorum of commonly operated endpoints is insufficient; a second RPC is corroboration, not proof of finality. Any source disagreement, reorg uncertainty, missing archive body, conflicting certificate, or inability to independently establish canonical finality means abstain. Operators record their distinct operator/ownership identities, network/genesis, archive sources, finality-verifier version, software version, and key custody/backup procedure. The deployment gate also requires a funded archive-retention plan for unresolved intents; without it, the committee is not operational.

## Canonical wire format

All structs below are Borsh v1 in the listed field order. Integers are fixed-width little-endian. Borsh strings are UTF-8 preceded by a little-endian `u32` byte length. Enums use the listed declaration order and `u8` discriminants starting at zero. `Option<T>` is byte `0` for `None`, or byte `1` followed by `T`. Hashes, keys, and signatures are fixed raw bytes, not hex or base58 text.

`RecoveryIntentV1` fields, in order:

1. `schema_version: u8` — exactly `1`.
2. `chain_id: String` — 1–128 lowercase ASCII bytes from `[a-z0-9._-]`.
3. `genesis_hash: [u8; 32]`.
4. `core_account_id: String` — canonical valid NEAR account ID, at most 64 bytes.
5. `instance_id: [u8; 32]` — unique random value fixed for this deployment.
6. `committee_epoch: u32`.
7. `transfer_id: u64` and `commitment_id: u64`.
8. `kind: TransferKindV1` — `Tranche = 0`, `EscrowRefund = 1`.
9. `tranche_epoch: Option<u32>` — `Some` only for `Tranche`; `None` only for `EscrowRefund`.
10. `token_account_id: String` and `recipient_id: String` — canonical valid NEAR account IDs, each at most 64 bytes.
11. `amount_raw: u128` — nonzero atomic token units; never JSON numeric text in the signed body.
12. `origin_method: OriginMethodV1` — `ClaimTranche = 0`, `RefundRemaining = 1`; must agree with `kind`.
13. `token_code_hash: [u8; 32]` — the network-specific Circle USDC code hash pinned by the recovery-enabled asset configuration.
14. `ft_transfer_deposit_yocto: u128` — exactly `1`.
15. `ft_transfer_gas_tgas: u64` — exactly `25` for this v1 configuration.

The NEAR hashes and Ed25519 keys are decoded to their exact 32-byte values before encoding. Account strings must parse as `near_sdk::AccountId` and round-trip byte-for-byte. Committee setup rejects duplicate, invalid, noncanonical, and small-order Ed25519 public keys.

**Frozen signature policy:** accept signatures only when they satisfy `ed25519-dalek 2.2.0` `VerifyingKey::verify_strict` semantics. This includes a canonical scalar, rejection of weak public keys, and strict point/malleability checks. The protocol-88 NEAR host implementation calls ordinary `Verifier::verify`, so a `true` result from `env::ed25519_verify` alone cannot authorize a certificate. The local feature-gated parser uses `verify_strict`; isolated Sandbox calls reject a noncanonical `S` scalar and small-order `R` point, and bootstrap rejects a weak committee key while remaining retryable. Other strict-encoding vectors still have standalone reference coverage only. The feature is disabled by default and has not been deployed.

The pinned host behavior is visible in [nearcore's protocol-88 verifier](https://github.com/near/nearcore/blob/bc4e9e8cfb03d9e82f027883055624e18576993e/runtime/near-vm-runner/src/logic/host.rs#L1975-L2066) and its [Ed25519 host tests](https://github.com/near/nearcore/blob/bc4e9e8cfb03d9e82f027883055624e18576993e/runtime/near-vm-runner/src/logic/tests/ed25519_verify.rs). The pinned build uses [ed25519-dalek 2.2.0](https://github.com/near/nearcore/blob/bc4e9e8cfb03d9e82f027883055624e18576993e/Cargo.lock). Its strict acceptance semantics are documented by the [versioned 2.2.0 API](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/struct.VerifyingKey.html). Host implementation details do not replace protocol-level rejection rules. Unsupported versions, invalid strings, inconsistent kind/epoch/method combinations, overflows, and trailing bytes are rejected.

Compute `intent_hash = SHA-256(domain || Borsh(RecoveryIntentV1))`. The domain is ASCII `LCP/NEP141/INTENT/V1` followed by one NUL byte; exact domain hex: `4c43502f4e45503134312f494e54454e542f563100`.

`RecoveryCertificateV1` fields, in order:

1. `schema_version: u8` — exactly `1`.
2. `intent: RecoveryIntentV1`.
3. `intent_hash: [u8; 32]` — recomputed from `intent` and required to match.
4. `origin_transaction_hash: [u8; 32]`.
5. `origin_receipt_id: [u8; 32]` and `origin_block_hash: [u8; 32]`, `origin_block_height: u64`.
6. `token_receipt_id: [u8; 32]`.
7. `token_action_index: u32` — exactly `0`.
8. `outcome_block_hash: [u8; 32]`, `outcome_block_height: u64`.
9. `outcome: TransferOutcomeV1` — `Success = 0`, `Failure = 1`. `Unknown` is not encodable.

Compute `certificate_digest = SHA-256(domain || Borsh(RecoveryCertificateV1))`. The domain is ASCII `LCP/NEP141/RECOVERY/V1` followed by one NUL byte; exact domain hex: `4c43502f4e45503134312f5245434f564552592f563100`. Each Ed25519 signature signs this exact 32-byte digest, with no additional prefix or prehash. Keys are `[u8;32]`, signatures `[u8;64]`; all signatures must verify independently against the same digest.

The Base64 argument decodes to `RecoveryEnvelopeV1 { certificate_bytes: Vec<u8>, signatures: Vec<SignatureEntryV1> }`, where each `SignatureEntryV1` is `{ public_key: [u8;32], signature: [u8;64] }`. With the field limits above, the maximum Borsh intent is 500 bytes, certificate 714 bytes, and envelope with five signatures 1,202 bytes. Require standard canonical Base64, decoded envelope ≤ 1,202 bytes, certificate ≤ 714 bytes, at most five signatures, and encoded text ≤ 1,604 characters. Check encoded and decoded bounds before allocation/verification. Use a bounded Borsh reader that checks every `Vec` and `String` length prefix against the field limit and remaining input before allocating; do not deserialize attacker-controlled lengths first and validate afterward. Parse both levels with exact-slice decoding, re-serialize and byte-compare, reject trailing bytes, noncanonical Base64, unsupported versions, invalid signatures, unsorted or repeated keys, and keys absent from the pinned epoch. Signature entries are strictly ascending by raw public-key bytes. Count distinct authorized public keys, never caller-supplied indices. A 0–3 signature envelope is invalid.

### Golden vectors

Before implementation, publish machine-readable Rust and signer-language vectors containing the complete intent bytes/hash, certificate bytes/digest, and four valid signatures. Include domain NUL bytes and raw hash byte order. Mutating any field, enum, domain byte, signature, signer order, or version must fail. Both implementations must reject trailing bytes, oversized lengths and invalid account IDs identically. Strict Ed25519 cases must include noncanonical `S`, weak/small-order keys, and noncanonical or small-order point encodings; compare the contract decision with the pinned strict verifier oracle.

An initial deterministic, synthetic Node.js vector set is in [tests/receipt-recovery-vectors](tests/receipt-recovery-vectors/README.md). A standalone Rust consumer independently reproduces positive encodings, exercises a bounded reference parser against valid maximum-size and malformed envelopes, confirms every recovery-certificate field/domain mutation invalidates the original signatures, and rejects malformed strict-Ed25519 cases. The feature-gated contract parser has now been exercised in protocol-88 Sandbox: 56 mutated/malformed envelopes were rejected without changing settlement state; bootstrap rejected a weak committee key without consuming its authority. A read-only Sandbox contract-VM probe also accepted a canonical maximum-size 5-of-5 envelope (500-byte intent, 714-byte certificate, and 1,202-byte decoded envelope); this synthetic message is not a pending transfer and cannot settle escrow. Independent reproduction of the Sandbox artifacts remains open.

## Receipt-to-intent decision procedure

This procedure is normative for every signer. The LCP contract itself does not validate NEAR receipt proofs; it validates the signed certificate against its own pending recovery intent. Each intent stores the exact token code hash selected from the approved, network-specific code-hash registry when the transfer is created. The signer compares observed **execution-time** code identity to that stored hash. It must not consult the current mutable registry to reinterpret an existing intent. A code hash not present in the review-approved historical registry makes a successful result `Unknown`.

1. Read the live LCP pending transfer and its stored `RecoveryIntentV1`; verify the chain ID, genesis, core account, instance, transfer ID, epoch, kind, amount, recipient, token, gas/deposit, and intent hash. Do not sign a transfer that is no longer pending.
2. Trace the finalized originating LCP action receipt from `origin_transaction_hash`. It must execute the intent's exact LCP method and commitment. Its log must contain `EVENT_JSON` with `standard: "lcp"`, `version: "1.0.0"`, `event: "token_transfer_intent"`, and one data object containing `schema_version: 1`, the decimal-string transfer ID, and lowercase-hex intent hash. Its receipt graph must contain exactly one direct child token action for this transfer; if an origin can schedule multiple token transfers, duplicate IDs/events exist, or the mapping is ambiguous, abstain. V1 therefore permits at most one outgoing USDC `ft_transfer` per origin invocation.
3. Require the token receipt predecessor to be `core_account_id`, receiver to equal `token_account_id`, and the receipt to contain exactly one action at index `0`: a function call to `ft_transfer`. Reject batched/multiple actions, other methods, extra arguments, duplicate JSON keys, or unsupported account/code versions.
4. Parse the JSON arguments with a duplicate-key rejecting parser. Require exactly `receiver_id`, `amount`, and `memo`; values must equal the intent recipient, canonical base-10 `amount_raw` with no leading zeroes, and `LCP1:<lowercase instance-id hex>:<transfer-id decimal>:<lowercase intent-hash hex>`. Require exactly one yoctoNEAR deposit and 25 Tgas. The memo is correlation data, not authentication.
5. Independently establish the token receipt's canonical finalized outcome and execution-time code identity using [the operator-policy annex](P2-USDC-RECEIPT-RECOVERY-OPERATOR-POLICY.md). For `SuccessValue`, require the one action's `AccountContract::Local(hash)` to equal the hash stored in this intent. For `Failure`, the exact finalized, single-action `ft_transfer` receipt means `Failure` under the pinned runtime's atomic receipt rollback semantics; no token state change from that receipt commits, even when code was unavailable before execution. This failure rule must pass the specified pre-execution and runtime rollback fixtures before implementation approval. A `SuccessReceiptId`, missing/nonfinal result, unresolved child promise, callback failure, transaction summary, log-only claim, provider conflict, unsupported code representation, or ambiguous ancestry is `Unknown`; never follow a downstream failure and call the original token action failed.
6. Construct one certificate with the exact receipt and block IDs. Recheck the pending intent immediately before signing. Persist a durable journal entry for `(instance_id, transfer_id)` and never sign another outcome or digest for that ID. A later callback/recovery race is resolved on-chain; signers do not alter an already settled result.

If the token receipt is a delegated/asynchronous operation, cannot be proven atomic, has an unexpected code hash, or otherwise falls outside these conditions, v1 must abstain. A certificate of failure is an attestation to this reviewed receipt interpretation, not mathematical proof supplied to the contract.

## Committee rotation and retained epochs

Initial configuration contains five unique Ed25519 public keys, the chain ID, genesis hash, current core account, unique instance ID, the USDC `active_code_hash` and reviewed historical code-hash allowlist, `last_rotation_generation: u64 = 0`, and a dedicated storage reserve ledger. The local feature-gated bootstrap captures the `new` initializer as its one-time authority, accepts the network genesis hash and random instance ID from that initializer, maps `mainnet`/`testnet` to their fixed Circle USDC accounts, and requires sorted canonical hashes and five sorted strong Ed25519 keys. The current implementation cap of eight approved USDC code hashes is a local bounded-storage choice, not a reviewed protocol limit; test and review it before relying on that capacity. It stores the initial five keys in the permanent used-key registry. A successful bootstrap consumes the authority and measures the configuration/keyset/registry storage against the attached NEAR reserve deposit; the full deposit is retained and cannot be withdrawn, including excess over measured storage. The genesis hash and instance ID are inputs, not runtime-derived facts, so the deployment operator must verify both independently, and deploy plus `new` must be atomic. This bootstrap has only passed compilation and is not a testnet acceptance. The allowlist and active hash are fixed for this instance; every transfer copies the active hash into its intent. A later code hash can enter the allowlist only through a separately reviewed configuration-upgrade design. It must not rewrite old intents, and old hashes stay available for their existing intents. Until an upgrade/configuration path is separately reviewed, an unlisted upgrade makes successful receipt recovery `Unknown`. Store the instance/configuration in versioned sidecar storage so existing top-level Borsh state layouts are not silently reinterpreted. A new instance ID is generated from a cryptographically secure off-chain source at fresh deployment and set once; it is public, not a secret.

One rotation proposal may exist at a time. Any caller may submit it only with a 4-of-5 current-epoch quorum (four or five unique signatures). `CommitteeRotationV2`, in Borsh field order, is `{ schema_version: u8, chain_id: String, genesis_hash: [u8;32], core_account_id: String, instance_id: [u8;32], old_epoch: u32, new_epoch: u32, proposal_generation: u64, new_keys: [[u8;32];5], activate_at_ns: u64 }`. Require `new_epoch = old_epoch + 1`, `proposal_generation = checked_add(last_rotation_generation, 1)`, unique keys sorted by raw bytes, no key used in any earlier epoch, and `activate_at_ns >= checked_add(env::block_timestamp(), 604_800_000_000_000)` (seven days in nanoseconds). The contract atomically stores the generation when it accepts the proposal; a rejected/OOG call does not consume it. If checked addition overflows, reject every further proposal. Cancellation and activation never decrement the generation. Sign the SHA-256 digest under ASCII `LCP/NEP141/COMMITTEE-ROTATION/V2` plus NUL (`4c43502f4e45503134312f434f4d4d49545445452d524f544154494f4e2f563200`). Activation is permissionless when `env::block_timestamp() >= activate_at_ns`.

Before activation, four or five current keys may cancel the exact pending proposal by signing `CommitteeRotationCancellationV2 { schema_version: u8, chain_id: String, genesis_hash: [u8;32], core_account_id: String, instance_id: [u8;32], old_epoch: u32, new_epoch: u32, proposal_generation: u64, proposal_digest: [u8;32] }`, with `schema_version = 2`, under ASCII `LCP/NEP141/ROTATION-CANCEL/V2` plus NUL (`4c43502f4e45503134312f524f544154494f4e2d43414e43454c2f563200`). `CommitteeRotationV2` also requires `schema_version = 2`. Cancellation is accepted only for the exact pending generation and digest while `env::block_timestamp() < activate_at_ns`; the pending slot is then free. Every cancelled or activated generation is permanently consumed. Old V1 proposal/cancellation bundles are rejected. A stale bundle, competing proposal with the same generation, or cancellation replay against a successor proposal is rejected.

Governance messages use the same canonical Borsh, sorted unique 4-of-5 signature, and bounded Base64/envelope parser rules as recovery certificates. `CommitteeRotationV2` is at most 449 bytes; its five-signature Borsh envelope is at most 937 bytes / 1,252 Base64 characters. `CommitteeRotationCancellationV2` is at most 313 bytes; its five-signature envelope is at most 801 bytes / 1,068 Base64 characters. Entry points may use the common 937-byte decoded / 1,252-character encoded cap, but must also enforce the message-specific cap before allocation. Four-signature maxima are 841 bytes / 1,124 characters for rotation and 705 bytes / 940 characters for cancellation. Publish golden byte/digest/signature vectors and mutation cases for both messages before implementation.

Every new transfer pins the active epoch and increments its pending count. Settlement decrements exactly that epoch's count. Retain the full old keyset until its count is zero; prune it only then. Keep each activated raw public key in a permanent used-key registry so it cannot be reused. Cap an instance at 32 committee epochs; at most 160 registry entries (5,120 raw key bytes) plus all 32 epoch keysets (another 5,120 raw bytes) can remain, before storage-key/metadata overhead. After the cap, no further rotation is permitted. A rotation proposer funds measured storage for the temporary proposal, next epoch keyset, five permanent registry entries, and preallocated credit records for proposal cancellation/activation and later keyset retirement. Cancellation or activation updates these funded records; it does not allocate a new payer-credit row. When an old epoch has no pending intents, remove its keyset and make its preallocated epoch credit withdrawable; permanent registry-entry bonds remain in the dedicated reserve and are never refunded. Repeated cancellations are storage-bounded by caller-funded records, even though generation count is unbounded. A fresh deployment may start a new instance only when it is not represented as recovering old liabilities. Lost/compromised old keys or exhausted rotation capacity can leave transfers pending permanently; no admin override exists.

## State, storage, migration, and atomic settlement

- Only transfers created with a complete v1 recovery intent after recovery configuration is installed are eligible. Existing current v2 sidecars lack genesis, instance, epoch, and recovery intent binding; they remain pending if their callback never reconciles. Do not backfill eligibility from old logs or infer native NEAR settlement from a missing token sidecar.
- Preserve the existing `last_allocated_transfer_id` across an in-place upgrade; it must be at least the highest ID ever allocated, and the next ID is `checked_add(last_allocated_transfer_id, 1)`. Persist the instance ID once and never reset it. Upgrade only from the finalized live state; do not restore a stale snapshot of the pending ledger, because it can resurrect already settled liabilities even if the counter is preserved. If instance, counter, current pending intents, and terminal settlement continuity cannot be proven, do not enable recovery. A fresh deployment has a fresh instance; it cannot recover another deployment's pending transfers.
- **Legacy cash-ledger bootstrap constraint (source review, 2026-11-15):** current commitments and pending transfers are `LookupMap`s keyed by sequential IDs, so their records can be scanned in bounded batches. Existing service-report refund credits instead use raw account-keyed storage keys with no account index, and `refund_excess` has no persisted attempt row. After an upgrade, contract state therefore cannot prove that every legacy credit and in-flight excess refund was included in `N`. Do not activate the global cash gate for an existing instance unless a separately reviewed process proves a complete legacy liability inventory. The clean deployment path is a fresh contract instance that initializes the ledger from zero and creates only recovery-eligible v1 transfers; it cannot inherit or recover predecessor pending transfers. Keep predecessor balances and obligations separate unless a complete migration is independently designed and proven.
- **Isolated testnet instance:** exercise the cash ledger and eventual recovery verifier on a dedicated child account such as `dev.livingcommitmentsprotocol.testnet`, created by `livingcommitmentsprotocol.testnet`. NEAR permits an account to create its direct subaccount; the child has independent contract state and access keys. This instance starts from zero protocol liabilities and does not inherit commitments, pending transfers, credits, configuration, or balances from the existing testnet contract. Fund, deploy, initialize, and configure it independently; point only local/preview environments at it. Never point the production domain at this account or upgrade the production contract before the post-hackathon release decision. See NEAR's [account model](https://docs.near.org/protocol/accounts-contracts/account-model) and [account creation guidance](https://github.com/near/near-cli#accounts).
- Allocate and fully bond-fund every `RefundCreditV1` row at admission, before asynchronous execution. A row is keyed by transfer/proposal/epoch ID and contains the immutable payer, state, accrued payable amount, checked withdrawal nonce, fixed-size current attempt amount/nonce fields, its terminal-sealed flag, live linked-record count, and its own measured storage bond. Each transfer or rotation preallocates all credit rows it may later need. Callbacks, recovery, cancellation, activation, and epoch pruning only update or remove existing rows; they never allocate a new payer-credit row. The row's own storage bond is never payable to its payer and is reclassified to the recovery reserve when the row is deleted.
- Define `RefundCreditV1` states as `Pending`, `Available`, `Withdrawing { amount, nonce }`, and `RefundPending { amount, nonce }`. `Pending` may hold admission excess already owed to the payer; that accrued amount is a liability even before withdrawal is enabled. The original bond for still-live intent/proposal/keyset storage is not yet a credit: it remains backing the live storage lock. On that record's deletion, move its recorded bond exactly once into its preallocated credit row. A terminal row becomes `Available` with the sum of its accrued excess and released bond. `Withdrawing` retains its full accrued amount as a payable liability until an exact success callback proves delivery. `RefundPending` also retains the full amount but cannot be retried until the post-refund solvency check passes. This counts Pending excess exactly once without counting a live storage bond as both storage and a cash credit.
- **Payer and callback authorization:** only `env::predecessor_account_id() == payer` may initiate withdrawal. The method has no receiver parameter; the only receiver is the immutable payer, and it withdraws the entire accrued amount. Reject zero amounts and checked-nonce overflow. Atomically persist the fixed-size `Withdrawing` state and attempt amount/nonce before creating the transfer. A private callback must require the current contract as predecessor, exactly one promise result, and an existing row whose ID, payer, state, amount, and nonce match the attempt. Any direct, duplicate, stale, or mismatched callback changes no state. Exact success deletes the row when the reserve is current; exact failure changes it to `RefundPending` with the same amount and nonce. If a byte-cost change or active revaluation prevents safe row removal after successful payment, the implementation releases that paid amount from Q and retains a zero-credit settled tombstone until reserve maintenance can close it. This tombstone behavior is an implementation detail added for the asynchronous storage-price boundary and has not yet received independent implementation review. A retry creates a checked next nonce only after the cash gate passes. Missing, multiple, unknown, or out-of-gas results leave the row in `Withdrawing`, payable but non-retryable. No caller may redirect or split a credit.
- **Conservative NEAR solvency rule:** before host-action materialization, define `C = env::account_balance()` after attached deposits have been credited; `S = env::storage_usage() × env::storage_byte_cost()`; `N` as all unpaid native escrow, payout, unspent operations, legacy refund, and other native liabilities not already represented by a recovery credit; `Q` as every accrued recovery-credit amount in `Pending`, `Available`, `Withdrawing`, or `RefundPending`; `F` as non-withdrawable recovery backing; and `X` as all remaining planned native value attached to outgoing transfer and function-call actions. Require `C >= S + N + Q + F + X` and zero storage-backing shortfall. After an action materializes, `C` reflects its deduction and that action is no longer included in the remaining `X`. Scheduling an action does not reduce payout/refund liabilities in `N` or `Q`; only an exact successful callback does. `Withdrawing` remains in `Q` until exact success.

  **Promise timing and cash gate:** the SDK builder stores actions locally; dropping it invokes the NEAR host APIs. The pinned nearcore host's transfer and function-call action handlers deduct attached value from the execution's current account balance. Therefore the candidate runs the cash preflight after liability/storage changes but before the first relevant builder is dropped, and includes the total planned receipt outflow as `X`. If a method materializes one builder before constructing a later action, its first preflight must already cover both outflows or a fresh check must account for the balance and remaining outflow at that point. The previous Sandbox probe sampled before `Drop`, so its exact-balance result is evidence for the pre-materialization gate only. The updated fixture explicitly drops the builder and records the post-materialization balance; run it and the exact-threshold, one-yocto-underfunded, no-action-on-failure, action-order, and multi-outflow checks before treating runtime behavior as accepted. A cash-gate panic after an action is materialized is not a safe rollback strategy.

  Include native payouts/refunds, storage-credit withdrawals, operations refunds, evaluator deposits, excess-storage refunds, and NEP-141's 1 yoctoNEAR function-call deposit in `X`. The local candidate persists exact attempt IDs for `refund_excess` and storage-credit withdrawals and preflights those values before creating promises. Native payouts/refunds and recovery credits retain non-retryable pending state until exact success; a fire-and-forget path remains a liability and cannot be retried. A failure callback keeps the liability, and the cash reserve covers the delay before NEAR's automatic transfer refund arrives. If callback execution is missing or out of gas, keep the liability and pending state indefinitely; do not infer success/failure from balance deltas or retry. **OutLayer execution deposits are the selected exception:** the configured amount is charged to `operations_authorized_spend_yocto` when the request is dispatched and is never restored after evaluator failure or timeout. Count it in `X` for the dispatch receipt, but do not create a persistent payable/refund liability or credit row for it. Protocol-level deposit refunds from a failed action receipt increase `C` only when actually credited to the contract; they never restore the commitment's operations budget. See the pinned [nearcore protocol-88 refund rules](https://github.com/near/nearcore/blob/bc4e9e8cfb03d9e82f027883055624e18576993e/docs/RuntimeSpec/Refunds.md).
- **Storage-bond and reserve accounting:** measure storage deltas for intents, credit rows, configuration, proposals, keysets, and registry records at current `env::storage_byte_cost()`. Store each live record's original storage bond `b_i` and current lock `r_i` separately from accrued credits. Let `S_R` be current recovery-record storage lock. For every live record, reserve `O_i = max(0, b_i-r_i)` as payer-specific bond excess and require treasury backing `G_i = max(0, r_i-b_i)` for any storage-price increase. Sum `O_i` and `G_i` per record so one payer's excess cannot cover another payer's deficit. `T` is explicitly funded, non-withdrawable reserve capital; `R_free = max(0, T - sum(G_i))`; `shortfall = max(0, sum(G_i) - T)`; and `F = sum(O_i) + R_free`. A permissionless payable top-up adds its attached deposit to `T`. A byte-cost increase moves reserve from `R_free` to `sum(G_i)` and any shortfall pauses admissions and native outflows; a decrease reduces `sum(G_i)` or increases the affected record's `O_i`, preserving the backing represented in `F`. For terminal payer-backed record `i`, let `b=b_i` and `r=r_i`. On release, remove `i` from `S_R`, `O_i`, `G_i`, and the live-bond ledger, add `b` exactly once to `Q`, recompute `R_free` and `shortfall`, and require `C >= S+N+Q+F` before committing. If the reserve is short, still commit any proven token settlement and terminal state, but retain the record and bond in the live-bond ledger; its preallocated row remains Pending with only previously accrued excess. After a top-up, any caller may retry the exact idempotent bond release. Never roll back a proven token outcome merely to release a NEAR storage credit. When a credit row is deleted after successful payment, do not pay its own bond to the payer: remove the row, add its original bond `b_i` to `T`, recompute its `O_i/G_i` contribution and the reserve, then recheck solvency. This transfers the row bond into treasury reserve without counting the released cash twice. Permanent registry/configuration/counter bonds remain locked. Preserve legacy commitment deposits only in their existing ledger and never credit them twice. Never use USDC, escrow, or evaluator operations funds to cover storage gaps or recovery credits.
- Bound persistent certificate/config data and intent lengths using the limits above. A successful or failed settlement removes only the exact pending intent, updates its preallocated credit row, and decrements one epoch count. `Unknown` or invalid certificates write nothing. Invalid submissions are caller-paid gas and create no storage. Any out-of-gas execution rolls back all writes, including credit mutation and event emission.
- Route both callback and recovery results through one internal `VerifiedTransferOutcome` settlement function. Callbacks produce success/failure only from exactly one explicit promise result; zero/multiple results, missing or mismatched v1 state, or unknown result contexts remain pending. Recovery produces a result only after all byte, key, receipt-policy, and pending-state checks. Re-read the intent immediately before mutation. The first valid serialized call consumes the transfer; any callback or certificate arriving later cannot alter it. Retries use new IDs.
- Emit the transfer ID, intent hash, outcome, and certificate digest (for recovery) in versioned events. Preserve the full certificate and source receipts in each operator's archive; on-chain state need only retain active intent/configuration and settlement events.
- Treat upgrade authority as a separate trust boundary: anyone able to replace core code can bypass these verifier rules. Testnet upgrade keys remain privileged. Before mainnet, deploy immutably or use the separately approved governance/timelock design; receipt recovery does not make an upgradeable core safe.
